B-1. The album request module: parse, pre-check, admit

Strong

Files: routes/album_flow.results_loading (130 lines, eight render_template error returns), _extract_job_params, routes/heatmap_flow._dispatch_heatmap_job, routes/api.validate_user, routes/__init__ checks; earlier cards 09-21 #2 (pipeline parameters) and 09-21b #2 (admission as one transaction), both OPEN.

Problem: parsing, the Last.fm pre-checks and job admission are one inline block. sort_mode, release_scope, decade, limit_results are never validated: a bad decade makes every album fail the release criteria, so the listener sees "no albums" instead of an error. One try wraps the user check, the privacy check and the registration-year hint; an outage in either pre-check is logged as "Registration year check failed ... proceeding" and the job starts anyway (controller verified), while the heatmap route answers 503 retryable. The ten job parameters are then re-passed positionally to the thread although the job record already holds them; admission (cleanup, slot, create, start, delete on failure) is written twice.

Solution: one module that turns a form into a validated album request or a typed refusal, one Last.fm pre-check answer shared by both routes, and one admission path that reads parameters from the job record.

Benefits: the owner's "no doomed submission" rule gets one owner and plain unit tests; WP-4 ("through the existing validators") gets validators that exist; the export route reuses it.

B-2. Provider failure lines say what failed, not what was searched

Strong

Files: utils.retry_with_semaphore (error_label), spotify.py, deezer.py, musicbrainz.py, orchestrator/_results.py, api_logging.py.

Problem: api_logging keeps search terms out of logs on purpose, but three providers build error_label as '{album}' by '{artist}' and the retry helper logs it at ERROR on every failed attempt (controller verified). For an export job those are names from the listener's upload; WP-3's acceptance forbids exactly that. The policy is a convention at seven call sites.

Solution: the retry helper owns what a provider-failure line may say: callers pass an operation key (e.g. Spotify search) and an opaque item index, never names.

Benefits: one place to test the privacy rule (capture logs, assert no names); the api_key redaction and this rule sit together.

B-3. One album aggregate, one publishing step, both sources

Strong

Files: orchestrator/__init__ (_fetch_job_albums, _process_filtered_albums, fetch_top_albums_async), unmatched.partition_albums_by_threshold, _results._build_results; earlier card 09-23 #1 (album calculation owns its answer, OPEN, F-B23-1).

Problem: the album aggregate is a dict with magic keys built by an inline loop and read by five functions; the steps after aggregation (publish each threshold exclusion, the "no album passes" terminal) sit in a Last.fm-only function whose contract is a sentinel (None = terminal already written). WP-2 writes a second producer and WP-3's export task would copy both blocks; WP-6 adds fields both producers must keep in step by hand.

Solution: extend Task 23: from normalized plays, one aggregate producing a typed album aggregate for both sources (two adapters: a real seam), and one publishing step that takes the aggregate and returns eligible albums or a terminal outcome through the job module.

Benefits: the export pipeline is a new source, not a copy; aggregation is testable without patching the Last.fm fetch.

B-4. A statistics module in Python; the browser only renders

Strong (before WP-6)

Files: static/js/heatmap.js (computeStreak, renderKpis), templates/results.html (Jinja sum of the displayed rows), orchestrator/_results.py, heatmap.py.

Problem: current streak, best day and daily average are computed in the browser in local time; the results page's "Scrobbles" total is a sum over the rows that happen to be displayed. WP-6 asks for UTC statistics from one pure helper fed by both sources; built as described, the streak would exist twice, and the JS half is testable only in a browser.

Solution: a Python statistics module (per-day counts or timestamps in, named facts with their population stated out) publishes facts on the job result; templates and scripts render.

Benefits: plain pytest coverage for every rule, UTC by construction, one population definition per figure.

B-5. Album metadata speaks one encoding

Strong

Files: enrichment.AlbumMetadata, cache.py (dict reads, positional 9-tuple writes with len(r) > 6 branches), orchestrator/_details.py (4-key dict), _deezer_fallback.py (7-key dict), _results._album_provider/_album_url; earlier card 09-21b #1 (provider adapter, PARTIAL) and 09-23 #3 (cache owns its operation, OPEN).

Problem: the provider contract is real, but after the providers the same six fields are re-encoded three times; two helpers exist only to rebuild fields one dict never carried; a six-tuple branch is reached only by the test that pins it.

Solution: the cache module takes and returns AlbumMetadata, and owns its connection lifetime and failure policy; results read attributes.

Benefits: the "shared cache rows hold no listening facts" contract has one write path to inspect; WP-6's per-album durations have one shape.
