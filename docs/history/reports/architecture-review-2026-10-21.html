What this is. A deepening review: refactors that turn shallow modules into deep ones, chosen for testability and AI-navigability. Every candidate below is a place where one fact -- a run's completeness, an exclusion's fields, a job's payload shape, a page's view data, a phase's collaborators, a poller's ordering rule -- lives in several modules at once, so changing it is a search rather than an edit.

What it is not. No interfaces are designed here, and this is not a re-run of the two earlier reviews: the overlap ledger records which existing owner each neighbouring idea already has, so the six below are the ones nobody owns.

Method

Where I looked, and why there

The hot spots first: the twenty-five commits before da4d8995 are provider semantics, the results and unmatched pages, the frontend gate and the job store's lifecycle. So the pass read the album pipeline (orchestrator/ and its four phase submodules), both pipelines' entry points (orchestrator.background_task, heatmap.heatmap_task), the job module and its store seam, the whole route package, the four providers, the cache, the result templates and every page script. The control plane (scripts/docsync/, scripts/dev/, tests/) was surveyed by shape and size; it has its own decomposition plan and its own findings, so nothing there is proposed.

The unit of judgement is the deletion test. Every candidate answers yes to "would deleting this concentrate complexity rather than move it?": deleting the six warning literals concentrates the degraded-run rule; deleting the three exclusion dict literals concentrates the exclusion shape; deleting the four inline mode checks concentrates the job-payload rule; deleting the duplicated render_template blocks concentrates the page's contract; deleting the facade's re-export block concentrates a phase's dependencies into its signature; deleting two of three hand-rolled pollers concentrates the ordering rule.

Vocabulary. The shared design vocabulary is used as the skill defines it -- module, interface, depth, seam, adapter, leverage, locality. The subject matter keeps the repository's own domain words (job, phase, results, unmatched, release scope) because those are the names the code already carries. This repository has no CONTEXT.md and no docs/adr/: docs/agents/global-rules.md, docs/ARCHITECTURE.md and docs/agents/FINDINGS.md are its architecture and decision authority, and those were read first.
Two global rules that shape the advice. Rule 3 (duplication buffer) says duplication is the correct answer until the third occurrence, so each card below names how many occurrences it is acting on -- candidate 6 is the third poller, which is what makes unifying it permitted rather than premature. Rule 4 (anti-corruption layer) is why candidates 1 and 2 push shape to the module that already owns the concept instead of inventing a new one. Rule 7 (deterministic diagnostics) is why nothing here asks a gate to guess: every candidate removes a place where a reader had to infer meaning from a string.

Candidate 01

One owner for "how complete was this run"

Strong

scrobblescope/jobs.py:232-262 (record_stat, record_partial_source) -- scrobblescope/orchestrator/__init__.py:126-133 and 396-399 (the Last.fm text is built here and recorded there), 215-218, 234-238, 254-258 (three provider sites) -- scrobblescope/orchestrator/_deezer_fallback.py:181-190 (the one guarded writer) -- scrobblescope/heatmap.py:184-192 (the same concept, string only, no kind) -- scrobblescope/routes/album_flow.py:418-446 (_partial_run_notice) -- static/js/loading.js:53-76 -- templates/results.html:66-74

Problem

"This run was degraded, and how" is written by six call sites, in two vocabularies: a single partial_data_warning string, which jobs.record_stat overwrites last-writer-wins, and a de-duplicated partial_data_sources list of kinds. Only one of the six writers guards its write (_deezer_fallback checks whether a warning already exists); the other five simply overwrite. So the first degradation's detail is destroyed by the second, and the two readers disagree about which half to trust: the loading page prints the stored string, while the Results page ignores it whenever a provider kind is present and composes fresh copy. Confirmed (D2): a run that dropped 3 of 12 Last.fm pages and then failed a Spotify token shows only "Spotify is temporarily unavailable for some albums..." -- the 25% data-loss sentence reaches nobody.

The heatmap pipeline copies the shape without the kind: heatmap.py records the string and never calls record_partial_source, so the second half of the pair is absent there and any reader that needs the kind sees nothing.

Solution

The job owns facts, not prose: a degradation is recorded as a kind plus its detail (dropped/expected pages, or which provider in which phase went unanswered), appended rather than assigned, and read back as a list. One renderer turns facts into the sentence each surface needs -- the Results notice keeps its single owner, and the loading line gets one too. partial_data_warning and partial_data_sources retire as separate keys; they are two halves of one fact, which is why they can disagree today.

Benefits

  • Locality: "what went wrong in this run" is one record
  • A seventh writer is one call, not a seventh string
  • The lost detail cannot be lost again
  • Tests assert facts, not sentences

How the tests improve. Today the pipeline tests assert a stat equals a sentence (test_orchestrator_fetch_spotify.py asserts partial_data_sources; test_heatmap.py counts warning calls), so any wording change breaks them while a lost fact passes. With facts, a paging-outage test asserts the record carries {"kind": "lastfm_pages", "detail": {"dropped": 3, "expected": 12}} and the renderer's own test owns the words -- two properties, two tests, neither guessing.

Why this is not F-B23-1. The album calculation F-B23-1 describes is where album rows and exclusions are assembled; this record is the run's completeness, written after the calculation and read by other surfaces. F-B23-1 is open and is not this.

What the export work will add. Batch 23's export path (skipped files, a partial parse) is a seventh writer to these same two keys, from a fourth module. Landing the owner first means that work writes one fact instead of a seventh wording plus a fourth copy of the guard.

Candidate 02

One owner for the album an exclusion describes

Strong

scrobblescope/unmatched.py:20-45, 100-136 (CATEGORY_METADATA, partition_albums_by_threshold) -- scrobblescope/orchestrator/_results.py:141-168 (release-scope entry, 11 fields) -- scrobblescope/orchestrator/_deezer_fallback.py:152-175 (no-match entry, 7 fields) -- scrobblescope/release_checks.py:155-170 (reads a field back off the entry) -- templates/unmatched.html:71, 144-236 -- static/js/unmatched.js -- scrobblescope/jobs.py:265-271

Problem

An "unmatched entry" is three different records. _results writes eleven fields, including provider, album_url and provider_release_date; _deezer_fallback writes seven, none of those three; partition_albums_by_threshold writes a third shape with failed_thresholds, shortfall, min_plays and min_tracks. Every consumer therefore reads by convention: the template carries a predicate that exists only to paper over the difference ({% if item.provider == 'spotify' or (reason_key != 'below_threshold' and not item.album_image and not item.provider) %}), and the correction worker reads provider_release_date straight off the entry -- a contract held by a comment in the writer and nothing in the reader.

The consequence is latency, not just tidiness: to answer "what does the Unmatched page know about an album, and why" you must read three writers, two reason tables (CATEGORY_METADATA plus the per-entry prose the grouper falls back to for legacy rows) and a 286-line template. WP-5's per-source wording would mean editing all three writers and the template predicate together, and nothing fails if one is missed.

Solution

The module that already owns the subject -- unmatched.py, which owns the reason codes and their copy -- owns the record too: one frozen value object for an excluded album, with one named constructor per reason (for_release_scope, for_no_match, for_below_threshold), and jobs.record_unmatched accepting the object rather than a dict literal. The grouper reads attributes; the template's compensating predicate collapses into "does this album have a provider page"; the correction worker's field becomes declared rather than assumed.

Benefits

  • One file answers "what does an exclusion carry"
  • The template loses a branch that exists only for heterogeneity
  • Legacy rows get one documented compatibility rule
  • The correction worker's field is declared

How the tests improve. The writers' tests assert dict literals key by key today, so a field the reader needs and the writer forgot passes everywhere. With one constructor per reason, each writer's test asserts which constructor was called with what facts, and a single test on the record proves every reason carries the fields its readers need -- the property the repository keeps re-checking by hand.

Why this is not B-5 or F-B23-1. B-5 ("album metadata speaks one encoding") is the enrichment record a provider returns, and F-B23-1 is the album calculation's return value; this is the exclusion record the Unmatched report renders -- a different fact, with different readers, and no owner on any plan.

Evidence. The field counts are read from the three writers at da4d8995. The template reads were grepped across the whole file, including the two ranges the indexer flagged as partially parsed (unmatched.html:192 and 200-204).

Candidate 03

One reader for a job, one rule for its payload

Strong

scrobblescope/routes/api.py:65-96 (/progress), 99-126 (/api/unmatched), 129-204 (/api/release_checks, with its own mode check and error envelope) -- scrobblescope/routes/heatmap_flow.py:163-202 (/heatmap_data, no mode check, spread payload) -- scrobblescope/routes/__init__.py:80-147 (_get_validated_job_context, the page routes' HTML failures) -- scrobblescope/jobs.py:470-517 (progress, exists, unmatched, context)

Problem

Five endpoints answer "give me job X's state", and each re-decides the same three things: whether the job is the right mode for this endpoint, what the envelope is, and what a failure looks like. The page routes got the mode rule right and even share it (_get_validated_job_context(expected_mode=...), whose docstring says "unavailable or wrong-mode jobs return 404, matching the APIs"); the service endpoints did not, so the rule now exists in four spellings -- the shared helper, one inline check in release_checks, and no check at all in the two others.

The unprotected one is the one that breaks: /heatmap_data builds its envelope by spreading the stored result into it, so an album job's list payload raises TypeError and answers 500 (D1, reproduced). A heatmap job id on /api/unmatched is answered as a valid empty report (D3). Both are the same missing rule, not two bugs. The failure envelopes diverge as well: /progress invents a synthetic 100%-complete error payload for a missing job, /api/unmatched answers {"count": 0, "data": {}}, and /api/release_checks has a third shape plus a deliberately not-a-real-status word ("error") that its own comment explains.

Solution

One read seam on the module that owns job state, e.g. a snapshot function that takes the job id and the mode the caller expects and returns either a typed view (mode, payload, progress, unmatched) or a typed refusal (missing / not_found / wrong_mode). The mode rule and the payload shape live there once; the endpoints keep only their own envelope, because that is genuinely theirs.

Benefits

  • D1 and D3 become unrepresentable, not fixed twice
  • Each endpoint's test shrinks to its own envelope
  • One test covers mode and payload for all five
  • A sixth poll endpoint is a call, not a re-implementation
  • Pollers get one failure vocabulary to stop on

How the tests improve. Today each endpoint's suite must re-prove the mode behaviour that only one endpoint implements, which is how the gap survived: no test asks /heatmap_data about a foreign job. With the seam, the cross-mode property is one table-driven test at the seam, and the endpoint tests stop carrying a responsibility they never had.

Why this is not F-B22-3. That finding owns ownership -- whether an unguessable job id is enough authorisation -- and says so explicitly for "every job-polling endpoint". This candidate is about the answer's shape and mode, and leaves the ownership decision to that owner. If the owner ever adds a session check, the seam is where it lands once.

Forward note. Batch 23's export path adds a third job mode and at least one more poll endpoint, which is three more chances to forget the same rule.

Candidate 04

One view model per page

Worth exploring

scrobblescope/routes/album_flow.py:449-560 (_render_results_page, two kwarg blocks) -- scrobblescope/routes/album_flow.py:122-330 (_render_unmatched_page) -- scrobblescope/routes/album_flow.py:24-72 (_extract_job_params, _filter_results_for_display, _get_filter_description) -- templates/results.html -- templates/unmatched.html

Problem

The Results page's contract is a literal keyword-argument block inside a route function, and it exists twice: the no-matches branch and the filled branch. The two have already drifted -- the empty branch omits release_check, spotlight_artists and the four top_artist_* names and passes filter_description instead -- which is exactly the failure mode of a duplicated contract: it is invisible until someone reads both blocks side by side. Answering "what does the Results page show for a degraded run" takes the route, both branches, _partial_run_notice, _filter_results_for_display, select_spotlight_artists and the 364-line template. _render_unmatched_page repeats the shape for its own page.

This is the "shallow interface" smell in its page-sized form: the interface (what the template is handed) is as complex as the implementation (how the page is assembled), so nothing is gained by the split and nothing is testable without a Flask client that renders HTML.

Solution

One function per page returning the whole mapping, with the route reduced to render_template("results.html", **view). Pure where it can be (given a job context and a progress payload, return the view), and the two branches become one branch with a flag, so the empty state cannot omit a name the template reads.

Strength, honestly. Worth exploring rather than Strong: it removes drift and buys testability, but it is not blocking any work package, so it should ride along with whichever change next touches the results route rather than open its own front.

Candidate 05

The seam the patcher draws

Worth exploring

scrobblescope/orchestrator/__init__.py:10-17 (the rule), 709-731 (the re-export block), 732-769 (__all__) -- scrobblescope/orchestrator/_search.py:1-10, _details.py, _cache.py, _deezer_fallback.py (each says it again) -- scrobblescope/routes/__init__.py:13-20, 281-291 -- scrobblescope/heatmap.py:259-266 -- scrobblescope/worker.py:76-109 (the counter-example in the same repository) -- the tests that patch scrobblescope.orchestrator.<name>, scrobblescope.routes.<name> and scrobblescope.heatmap.release_job_slot

Problem

Every collaborator a phase calls is a module global, re-exported through the package facade, because the phase reads it as _orchestrator.fetch_spotify_album_details_batch so that an existing mock.patch("scrobblescope.orchestrator.X") still lands. That is the seam: the interface is the test surface. The code says the quiet part out loud -- "Moving an import out of this file without also checking every submodule that reads it this way silently breaks that patch path" -- and repeats the warning in four more modules, plus the equivalent in routes/__init__.py and heatmap.py.

The cost is measurable. The facade's __all__ lists 36 names, most of which nothing in that file calls; the file is 770 lines and 29 KB, and its job is "the import surface the suite patches". A module boundary cannot move without auditing the test suite, and a dependency added to a phase silently becomes a new public name. A phase's own signature does not say what it depends on, so reading one in isolation does not tell you what it can reach.

The same repository already shows the alternative: worker.run_coroutine_in_new_loop takes make_loop and release_slot as parameters with local defaults, and both callers pass their own names explicitly -- "so callers keep their own patchable name". The pattern exists; it was applied to the loop protocol and nowhere else.

Solution

No interface is designed here, but the shape is the one already in worker.py: a phase takes the collaborators it uses as parameters, with the current module globals as defaults, and the two entry points pass them. The re-export block becomes deletable, the ordering constraint ("they must be imported last") disappears, and the five "read through the facade" warnings go with it.

Cost, stated plainly: this touches many mock.patch targets in tests/services/test_orchestrator_* (25-55 KiB each). Parity tests exist, and AGENTS.md's Proposal and Design Rules require them before a structural refactor -- which is why this is a candidate to schedule, not a drive-by.

Benefits

  • Locality: a phase's dependencies are readable in its signature
  • The 30 KB facade shrinks to the entry points
  • Module boundaries can move without a test audit
  • Six copies of the same warning disappear
  • Leverage: one pattern, already proven in worker.py

How the tests improve. A phase test stops needing the package namespace to be shaped a particular way: it passes a fake and asserts the phase's answer. The compensation layer is visible in the suites today -- test_orchestrator_fetch_spotify.py is 55 KiB and much of it is about the module's wiring rather than about what the pipeline decides.

Not the deferred "generic provider framework". The earlier report's ledger records a provider framework as an existing deferred decision, and this does not ask for one: no new provider abstraction, no registry, no plugin protocol. It asks only that a function receive what it calls.

Evidence. The warning text quoted above is in orchestrator/__init__.py's module docstring and is repeated in _search.py, _details.py, _cache.py and _deezer_fallback.py; the same reasoning appears in routes/__init__.py and in the two entry-point comments in heatmap.py.

Candidate 06

One poller in the browser

Worth exploring

static/js/loading.js:33-35, 156-205 (four guard variables, shouldPollAgain, fetchProgress) -- static/js/heatmap.js:656-666, 1089-1181 (startPolling, stopPolling, pollProgress, the same four names, its own transient-error branch) -- static/js/results-release-checks.js:18-33, 117-170 (POLL_MS, a timer, a visibilitychange pause) -- tests/frontend/ (the browser harness) -- tests/test_template_shell.py:920-930 (asserts script text)

Problem

Three pages each hand-roll the same poller, and this is the third occurrence -- which is the point at which this repository's own duplication rule stops protecting the copies. Each has: an interval, an in-flight guard, a sequence guard so a late reply cannot overwrite a newer one, a stop-on-terminal rule, and a "keep going on a transient network error" decision. The sequence guard alone is spelled four times in two files with identical names (pollSeq, latestAppliedPollSeq, pollInFlight, plus errorDetected in one and stopped in another), and the guards have already diverged: only results-release-checks.js pauses while the tab is hidden, and only heatmap.js has the explicit transient-error branch. The behaviour differences are not decisions anyone wrote down; they are what happens when one concept is implemented three times.

That heatmap.js also carries rendering, tooltip ownership, keyboard navigation, theme observation and the JPEG export in the same 1716-line file means the polling third cannot be read on its own -- locality is the casualty, not line count.

Solution

One small module with a pure step function ("given this reply and this state, what next?") plus a thin timer wrapper that owns the interval, the in-flight and sequence guards and the hidden-tab pause. Each page supplies its URL, its terminal test and its render callback. Nothing about the pages' markup changes.

A pure step function can be tested there for the property none of the three copies proves today -- that a reply from an older request cannot win -- while test_template_shell.py stops being the place where polling is "covered" by asserting that the script text contains 'pending' and 'running'.

Not F-B21-18's browser seam. That finding owns the harness itself (how many pages are covered, how it is wired); this is about the code under test, and it makes the harness's job smaller.

Gate note. The frontend gate has checks that drive these pages end to end (check_pipeline_state_machines), so a shared poller is exercised by the existing gate as well as by the new unit test -- the extraction does not create a coverage hole.
