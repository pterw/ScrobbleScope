CI (`.github/workflows/test.yml`) runs the same installs on Linux. No `.env`
and no Postgres are needed for the suite or the gates. Three things a cloud
sandbox does differently, all met in the first cloud session:

- **The Tailwind download fails** in the `tailwind-css-drift` hook: Python
  3.13's strict certificate checks reject the sandbox proxy's CA ("CA cert
  does not include key usage extension"). Fetch the three pinned artifacts
  with `curl` into `scripts/bin/` (gitignored); `tailwind_build.py` checks
  each against its pinned SHA-256 on every run, so verification is not
  weakened. The URLs and hashes are `required_artifacts()` in
  `scripts/dev/tailwind_build.py`.
- **The frontend gate cannot run.** The pinned Playwright wants browser
  builds the sandbox does not ship, and the sandbox forbids
  `playwright install`. The root cleanup's Task 4 moves the gate's
  manifest: run its frontend gate locally or rely on CI's `quality-gate`,
  and say which in its Section 4 entry.

  ask the owner for the rule and line from the Codacy UI.

## 4. How the work is run

Subagent-driven development: one fresh implementer per task, then an
independent review and an independent gate run, then fix rounds until clean.

- **Workspace.** Create `.superpowers/sdd/<date>-batch23-wp0-root-cleanup-<where>/`.
  Copy `.superpowers/cloud-kit/constraints.md` into it as `constraints.md`,
  and keep a `progress.md` ledger there: one line per dispatch, result,
  review verdict, gate result and ruling.
- **Agents.** Dispatch the general-purpose agent, prompt opening "Follow
  `.superpowers/cloud-kit/agents/<name>.md` as your instructions.", with the
  inputs that file lists:
  - `sdd-implementer` (sonnet): WORKSPACE, BRIEF, REPORT, BASE, plus a context
    file for anything the brief cannot know (pre-flight facts, owner
    rulings). Resume the same implementer for fix rounds.
  - `sdd-reviewer` (sonnet): BRIEF, REPORT, DIFF, WORKSPACE, REVIEW path.
    Always add: never edit the working tree (Lesson L9); sweep the whole
    task range for stale copies of every fact the task changed (L12); check
    the plan checkboxes and count sites (L11).
  - `gate-runner` (haiku): WORKSPACE, REPO, BASE, LOG_DIR. Check LOG_DIR holds
    a log per gate, and that every code its summary quotes is in a log,
    before recording its verdict (L10, L13).
  - `sweeper` (haiku): TERMS, with `REGEX: yes` and `\b` for ids such as
    `F-B21-6\b`. Spot-check "no other hits" with one `git grep -c -P`.
  - **Never dispatch Opus.** Sonnet for implementers and reviewers, haiku for
    gate-runner and sweeper (owner cost policy).
- **Briefs and review packages** without the plugin scripts:

  ```bash
  # Brief: the task's section of the plan, up to the next heading or rule.
  awk '/^### Task 3:/{f=1;print;next} f&&(/^### Task /||/^## /||/^---$/){exit} f' \
    docs/superpowers/plans/2026-09-24-batch23-wp0-root-cleanup.md > "$WS/task-3-brief.md"
  # Review package: commits, stat and the net diff for BASE..HEAD.
  { git log --oneline BASE..HEAD; git diff --stat BASE..HEAD; git diff -U10 BASE..HEAD; } \
    > "$WS/review-BASE..HEAD.diff"
  ```
- **One writer per file.** Two writers may run at once only on disjoint
  files (owner ruling, 2026-09-24); a file never has two writers. A reviewer
  and a gate-runner may run side by side; neither writes.
- **Before recording anything, verify it.** Re-read the claim at source, or
  run the command. A subagent's summary is not evidence (Lessons L9-L10, L13).
- **Pushing.** Hold a task's commits until its review is recorded clean, then
  push with the owner's go. The stop hook asks to push after every turn;
  decline it until then.

## 8. Traps

- A `WP-<digit>` token in a Section 4 heading marks the work package complete
  (L3). Check with `grep -n "^### .*WP-[0-9]" docs/agents/PLAYBOOK.md`. This
  file's first version broke it; the fix landed in `1d16e18`.
- A closed finding's status line is the bare outcome only (L5); any trailing
  text fails DOC015.
- A plan's last task extracts with the sections after it; cut the brief at
  the task's closing rule.
- Reviewers sometimes label their own findings "plan-mandated". Check the
  brief's literal text before deferring anything.
- Pre-commit's `worktree-alignment` hook prints WT000 since `a945d25`, and
  WT010 while the tree is dirty; an `ERROR WT005` against `origin/main`
  returns only if `main` moves, and is advisory (R6).
- **A plan's own text can break R1.** Task 1's literal Section 4 heading
  carried a `WP-0` token. Grep every heading a brief dictates before
  writing it.
- **A test adapted to fit a fixture can stop testing the change.** Task 2's
  first override test passed with the override reverted. Prove a new
  test by mutation in a scratch copy (`git archive HEAD | tar -x -C
  <dir>`): revert the change there and watch the test fail.
- A brief written before an earlier task landed can name stale sites. Task 5's
  brief grepped for `DOC001-DOC02` and missed a backticked range; grep the
  concept, in every spelling, at HEAD.
- **The owner's own changes can appear in the tree mid-task** (staged
  `gh aw` files, an editor re-saving a file). Never stage, revert or commit
  them unasked. `pre-commit run --all-files` runs its whitespace fixers over
  them, so while they sit in the index run the gates in a separate detached
  worktree at the task commit (`git worktree add --detach <short path>
  <sha>`, removed afterwards) and tell implementers not to run pre-commit
  standalone.
- **Workflow files need the `workflow` permission to push.** The
  fine-grained token some sessions load from `.env` lacks it, and pushing
  a branch that adds `.github/workflows/*` fails with 403 under it. A cloud
  session's git proxy pushed them without trouble (`a945d25`).
- **gh-aw workflows are compiled.** After editing `repo-assist.md`, run
  `gh aw compile repo-assist` and commit the regenerated `.lock.yml`; a
  change to its memory-validation script also needs `--approve`, after
  reviewing it. A cloud sandbox may lack the `gh aw` extension: then leave
  the workflow edit to a local session.
